## 一、项目概述

### 1.1 项目背景

随着高校招生规模扩大，图书馆、教学楼自习室座位资源与学生需求之间的矛盾日益突出。传统自习室管理以"先到先得"为主，普遍存在以下问题：

1. **占座现象严重**：学生用书本、水杯等物品长期占用座位，实际到座率低，资源浪费；
2. **管理成本高**：管理员需要人工巡查、登记座位状态，效率低且无法实时掌握座位使用情况；
3. **信息不透明**：学生无法提前获知座位空闲情况，到馆后才发现无座，体验差；
4. **缺乏数据支撑**：自习室利用率、时段热度等数据无法统计，难以支撑场馆运营决策。

针对上述问题，本系统设计并实现一套"**线上预约 + 视觉识别座位检测**"闭环的校园自习室预约管理系统：学生可在线查看自习室实时座位状态并预约；系统通过摄像头对座位进行视觉识别，自动判定座位占用情况，与预约数据联动，实现"预约—签到—入座—离座"的全流程智能管理，有效治理占座、提高座位利用率。

### 1.2 建设目标

1. 实现学生自助注册、登录、预约、取消、签到、查看预约记录的全流程线上化；
2. 实现管理员对用户、自习室、座位、预约记录、检测日志的全面管理及统计报表可视化；
3. 基于 OpenCV 背景建模（冻结背景策略）实现座位占用视觉检测，实时更新座位状态，与预约联动（超时未签到释放、疑似占座提醒、离座释放）；
4. 保证系统在高并发预约场景下的数据一致性（离散时段模型 + 数据库唯一索引防重叠抢座）；
5. 提供清晰可扩展的接口设计与数据库设计，支持后续功能扩展（如 YOLOv8 目标检测、人脸识别签到、消息推送等）。

### 1.3 系统特色

| 特色 | 说明 |
|---|---|
| 预约+检测闭环 | 预约系统与视觉检测联动，预约状态由视觉识别结果驱动，非简单人工维护 |
| 离散时段模型 | 预约按固定时段（默认 30 分钟粒度）进行，配合双唯一索引从数据库层面根治并发抢座 |
| 冻结背景视觉检测 | OpenCV MOG2 + learningRate=0 冻结背景 + 空场初始化 + 每日重基线，可检出"静止的占座人/物"，与治理目标一致；检测器接口化，可扩展 YOLOv8 |
| 可视化座位地图 | 前端以座位网格图实时呈现空闲/已预约/使用中/禁用状态，所见即所得 |
| 技术栈主流 | Spring Boot 3 + Vue 3 + MyBatis-Plus + MySQL，前后端分离，符合当前主流开发范式 |

- 同一用户同一日期同一时段仅允许预约一个座位（数据库唯一索引兜底）；
- 取消截止时间 = 时段开始前 30 分钟；超过截止时间未签到，系统按规则释放并计违约；
- 违约惩戒：违约累计满 3 次，暂停预约权限 7 天；
- 不允许预约过去时段、非开放时段。

## 三、总体设计

### 3.1 系统架构

系统采用前后端分离的 B/S 三层架构：

```
┌────────────────────────────────────────────────────────────┐
│                        用户层                              │
│   学生浏览器 / 管理员浏览器（Vue3 SPA）                     │
└──────────────┬──────────────────────────┬─────────────────┘
               │ HTTPS / JSON             │
┌──────────────▼──────────────────────────▼─────────────────┐
│                    服务端（Spring Boot 3）                 │
│  认证模块 │ 自习室模块 │ 座位模块 │ 时段/预约模块 │ 统计模块│
│  视觉联动定时任务（轮询视觉服务 → 更新座位状态 → 状态机）  │
└──────────────┬──────────────────────────┬─────────────────┘
               │ REST(HTTP) 轮询           │ JDBC
┌──────────────▼─────────────┐  ┌─────────▼─────────────────┐
│   视觉识别服务（Python）    │  │        MySQL 8            │
│  FastAPI + OpenCV          │  │  user/room/seat/slot/      │
│  摄像头拉流→冻结背景MOG2→   │  │  reservation/seat_log/    │
│  ROI判定→GET /detect       │  │  admin_audit_log          │
└────────────────────────────┘  └───────────────────────────┘
```

**架构要点**：

1. **前端**：Vue 3 + Vite + Element Plus + Pinia + Vue Router + Axios + ECharts，单页应用；
2. **后端**：Spring Boot 3 提供 RESTful API，MyBatis-Plus 完成 ORM 数据访问，JWT 实现认证，定时任务调度视觉状态同步；
3. **视觉服务**：独立 Python 进程（FastAPI + OpenCV），与后端通过 HTTP 解耦；**集成模式统一为"后端定时轮询视觉服务 `GET /detect`"**，职责清晰、故障隔离、便于演示；
4. **数据库**：MySQL 8，InnoDB 引擎，utf8mb4 字符集。

### 3.3 视觉识别方案设计（座位占用检测）

#### 3.3.1 方案选型对比

| 方案 | 原理 | 优点 | 缺点 | 本系统定位 |
|---|---|---|---|---|
| 目标检测（YOLO 系列） | 深度神经网络回归目标框与类别 | 精度高、可识别具体对象（人/书/包），对遮挡鲁棒 | 需模型权重与训练数据，依赖较重 | 扩展方向（`yolo_detector.py` 预留） |
| **背景建模（MOG2，冻结背景）** | 高斯混合模型描述背景，前景差分 | 无需模型、计算量小、适合固定机位；冻结背景后可检出静止目标 | 对光照突变敏感；依赖背景基准准确 | **本系统默认采用** |
| 帧差法 | 相邻帧像素差检测运动目标 | 最简单、速度最快 | 静止目标完全失效（占座者不动则测不出） | 不采用 |

#### 3.3.2 检测方案核心设计（关键修正）

> **设计要点**：自习室治理占座的本质是检出"与空场景不一致的静止目标"（静坐的人、占座的书包水杯）。
> 默认 MOG2 会随学习率把静止前景吸收进背景，导致静坐学生被误判为空座。
> 因此本系统采用 **冻结背景策略**：`learningRate=0`（背景模型不自动更新），
> 任何进入场景且与空背景存在差异的目标（无论是否运动）都会持续显示为前景并被判定为占用。

```
摄像头（RTSP/USB/本地视频）
        │ 抽帧（默认 1 fps，可配置）
        ▼
预处理：缩放 → 灰度 → 高斯模糊去噪
        ▼
MOG2 背景建模（learningRate=0，冻结背景）
        │ 背景基准：空场初始化（首帧/管理员触发/每日闭馆自动重建）
        ▼
前景掩码（静止人/物同样检出）
        ▼
形态学处理：开运算去噪点 → 闭运算填充空洞
        ▼
轮廓检测 → 过滤：面积阈值、宽高比范围（排除噪声与误检）
        ▼
与预配置的"座位 ROI 区域"做重叠度判定（重叠面积占比 ≥ 0.5）
        ▼
输出：{seat_id: {occupied: true/false, confidence: 0~1}}
        ▼
后端定时任务轮询 GET /detect → 更新 seat.status → 翻转时写 seat_status_log
```

**关键设计点**：

1. **座位 ROI 配置**：管理员在视觉服务配置文件 `config.json` 中以 JSON 预标定每个座位的图像坐标区域，一次标定、持续使用；
2. **背景基准管理**：① 首帧初始化；② 管理员可手动触发"重置背景"；③ 每日闭馆后定时任务自动重建背景，消除光照与陈设漂移；④ 光照突变时检测结果大面积异常，可触发"背景自检告警"提示管理员重置；
3. **占用判定规则**：目标轮廓与座位 ROI 重叠面积占比 ≥ 阈值（默认 0.5）判定为占用；连续 3 帧一致才翻转状态，抑制抖动误判；
4. **状态写库治理**：`seat_status_log` **仅在状态翻转时写入**（避免 5s 粒度海量日志），记录 `occupied`、`confidence`、`detector`（检测器标识）与时间；按日归档清理；
5. **集成模式**：统一为**后端定时（5s）轮询**视觉服务 `GET /detect?room_id=`；视觉服务无状态、无回调；后端处理失败重试（下一轮自动补偿）与乱序（按 detect_time 取新弃旧）；
6. **降级策略**：视觉服务不可用时，座位保留最近一次检测结果，管理员可人工修改座位状态；预约核心功能不受影响；违约判定区分系统故障（见 6.3）；
7. **可扩展性**：检测器采用接口抽象（`BaseDetector`），默认 `Mog2Detector`（冻结背景），预留 `YoloDetector` 扩展位——目标检测（人 + 书本/水杯类别）可无缝替换，实现更鲁棒的静止占座判定。

#### 3.3.3 视觉识别与预约业务的联动规则

| 场景 | 规则 |
|---|---|
| 预约成功 | 座位状态置为"已预约"（视觉检测不参与，预约数据驱动） |
| 到馆签到 | 学生点击签到 + 后端查询视觉检测结果：视觉可用且座位为空 → 提示学生核实（可强制签到）；视觉可用且座位占用 → 签到成功；视觉不可用 → 按时间窗直接签到成功 |
| 超时未签到 | 时段开始 30 分钟后仍未签到：视觉确认座位为空 → 释放并**计违约**；视觉服务不可用 → 释放但**不计违约**（技术故障不惩罚学生） |
| 疑似占座 | 座位无有效预约但视觉持续检测占用（连续 ≥ 10 分钟）→ 标记"疑似占座"，提醒管理员 |
| 离座释放 | 已签到学生离开后，视觉连续 30 分钟检测座位为空 → 预约置为"提前结束"，座位释放，剩余时段作废 |

**座位实时状态（seat.status）写入规则（单一数据源）**：`seat.status` 仅由"视觉状态同步定时任务"统一计算写入，
优先级为：① 座位禁用 → 0；② 当前时段存在进行中预约（status∈{0,1}）→ 已签到为 3（使用中）、待签为 2（已预约）；
③ 无进行中预约 → 视觉占用为 3、视觉空闲为 1。预约创建/取消等业务操作**不直接修改** seat.status
（仅影响规则②的判断输入），避免多写者冲突。
"疑似占座"（无预约但视觉占用）不设独立状态位，通过查询检测日志（seat_status_log）与管理端视觉监控页实时呈现。

## 四、数据库设计

### 4.1 实体关系（ER）

- **user**（用户）1—N **reservation**（预约记录）
- **room**（自习室）1—N **seat**（座位）；1—N **slot**（时段）
- **seat**（座位）1—N **reservation**（预约记录）；1—N **seat_status_log**（座位状态检测日志）
- **slot**（时段）1—N **reservation**（预约记录）
- **user**（管理员）1—N **admin_audit_log**（操作审计）

### 4.2 数据表设计

#### 4.2.1 user —— 用户表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 用户ID |
| student_no | VARCHAR(20) | UNIQUE, NOT NULL | 学号 |
| username | VARCHAR(50) | NOT NULL | 用户名 |

#### 4.2.2 room —— 自习室表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 自习室ID |
| name | VARCHAR(50) | NOT NULL | 自习室名称 |
| building | VARCHAR(50) | NOT NULL | 楼栋 |
| floor | INT | NOT NULL | 楼层 |
| capacity | INT | NOT NULL | 座位容量 |
| open_time | TIME | NOT NULL | 开放时间 |
| close_time | TIME | NOT NULL | 关闭时间 |
| status | TINYINT | NOT NULL, DEFAULT 1 | 状态：0停用 1开放 |

#### 4.2.3 seat —— 座位表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 座位ID |
| room_id | BIGINT | NOT NULL, FK→room.id | 所属自习室 |
| seat_no | VARCHAR(20) | NOT NULL | 座位编号（如 A-01） |
| row_no | INT | NOT NULL | 排号（座位图坐标） |
| col_no | INT | NOT NULL | 列号（座位图坐标） |
| seat_type | TINYINT | NOT NULL, DEFAULT 0 | 类型：0普通 1靠窗 2电源 3隔断 |
| status | TINYINT | NOT NULL, DEFAULT 1 | 实时状态：0禁用 1空闲 2已预约 3使用中 |

约束与索引：

- `UNIQUE KEY uk_room_seat (room_id, seat_no)` —— 同一自习室座位编号唯一；
- `UNIQUE KEY uk_room_pos (room_id, row_no, col_no)` —— 座位图坐标不重叠；
- `KEY idx_room (room_id)`。

#### 4.2.4 slot —— 时段表（离散时段模型核心）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 时段ID |
| room_id | BIGINT | NOT NULL, FK→room.id | 所属自习室 |
| start_time | TIME | NOT NULL | 开始时间 |
| end_time | TIME | NOT NULL | 结束时间 |

约束：`UNIQUE KEY uk_room_slot (room_id, start_time)`。

> **时段非重叠保证**：区间重叠无法用数据库唯一索引表达（MySQL 无区间索引），
> 因此由服务端在时段新增/修改时强制校验：新时段不得与该房间既有时段存在时间重叠
> （即不得存在 `start_time < 新end_time AND end_time > 新start_time` 的既有时段）。
> 该校验是"离散时段防重叠承诺"的前提防线（见 5.5 管理端时段接口）。

> 时段由管理员预配置（默认将开放时间按 30 分钟切分，如 08:00-08:30、08:30-09:00……）。
> 预约关联到具体时段后，唯一索引即可从数据库层面杜绝任何形式的重叠。

#### 4.2.5 reservation —— 预约记录表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 预约ID |
| user_id | BIGINT | NOT NULL, FK→user.id | 预约学生 |
| room_id | BIGINT | NOT NULL, FK→room.id | 自习室 |
| seat_id | BIGINT | NOT NULL, FK→seat.id | 座位 |
| slot_id | BIGINT | NOT NULL, FK→slot.id | 时段 |
| reserve_date | DATE | NOT NULL | 预约日期 |
| status | TINYINT | NOT NULL, DEFAULT 0 | 状态：0待签到 1已签到 2已完成 3已取消 4违约 5提前结束 |
| create_time | DATETIME | NOT NULL | 创建时间 |
| sign_time | DATETIME | NULL | 签到时间 |

约束与索引：

- **条件唯一索引（生成列，防重叠抢座核心设计）**：
  - `active_key = IF(status IN (0,1), CONCAT(seat_id,'_',reserve_date,'_',slot_id), NULL)`，
    其上建 `UNIQUE KEY uk_seat_active (active_key)` —— 同一座位同一日期同一时段仅允许一条**进行中**预约；
  - `active_user_key = IF(status IN (0,1), CONCAT(user_id,'_',reserve_date,'_',slot_id), NULL)`，
    其上建 `UNIQUE KEY uk_user_active (active_user_key)` —— 同一用户同一日期同一时段仅可约一个座位；
- `KEY idx_user (user_id)`、`KEY idx_seat_date (seat_id, reserve_date)`；
- `KEY idx_status_time (status, reserve_date, slot_id)` —— 支撑违约扫描/释放定时任务。

> **并发正确性说明（含取消释放）**：采用 MySQL 生成列条件唯一索引——`status ∈ {0,1}`（待签到/已签到）
> 时 active_key 为实际值、占用唯一性；`status ∉ {0,1}`（已取消/违约/已完成/提前结束）时 active_key 为 NULL、
> 不参与唯一性判定。因此取消、违约、自然结束后的预约**不会永久占用唯一索引**，
> 同一座位同一时段可被重新预约，与 U5 取消规则自洽。离散时段模型下任意两个进行中预约
> 要么时段完全相同（被唯一索引拒绝）、要么时段不同（不重叠），不存在自由时段模型的"部分重叠"漏洞。
> 业务层"先查后插 + 事务"仅用于友好提示，数据库唯一索引是并发安全的最终防线。

#### 4.2.6 seat_status_log —— 座位状态检测日志表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 日志ID |
| seat_id | BIGINT | NOT NULL, FK→seat.id | 座位 |
| occupied | TINYINT | NOT NULL | 是否占用：0空 1占用 |
| confidence | DECIMAL(5,2) | NULL | 检测置信度 0~1 |
| detector | VARCHAR(20) | NOT NULL, DEFAULT 'mog2' | 检测器标识 |
| detect_time | DATETIME | NOT NULL | 检测时间 |

索引：`KEY idx_seat_time (seat_id, detect_time)`。

治理策略：**仅在状态翻转时写入**（正常场景下座位状态稳定，日志量可控）；按日分区，保留 N 天后归档清理（由管理员配置）。

#### 4.2.7 admin_audit_log —— 管理员操作审计表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 日志ID |
| admin_id | BIGINT | NOT NULL, FK→user.id | 操作管理员 |
| action | VARCHAR(50) | NOT NULL | 操作（如 FORCE_CANCEL / SEAT_EDIT） |
| target_type | VARCHAR(30) | NOT NULL | 对象类型（reservation/seat/room/user） |
| target_id | BIGINT | NOT NULL | 对象ID |

### 4.3 预约状态机

```
       创建预约            签到            时段自然结束
   ┌──────────┐        ┌────────┐        ┌────────┐
   │0 待签到  ├───────►│1 已签到├───────►│2 已完成│
   └────┬─────┘        └───┬────┘        └────────┘
        │                  │离座释放(视觉连续30min空)

        │             ┌────────┐

        │             └────────┘

```

## 六、核心业务流程

### 6.1 预约流程

1. 学生登录 → 选择自习室 → 选择日期；
2. 加载自习室时段列表（`/slots`）与座位图（`/seats?date=&slotId=`），座位状态含该时段预约标记；
3. 学生选择座位与 1~N 个连续时段，发起预约；
4. 后端事务处理：校验（本人未被禁约、时段在开放时间内、非过去时段、连续时段）→ 批量插入预约记录（每时段一条）→ 任一冲突则整体回滚并返回 409；
5. 数据库唯一索引（`uk_seat_slot` / `uk_user_slot`）兜底并发，捕获重复键异常返回友好提示；
6. 预约成功，对应座位在所约时段标记"已预约"。

### 6.2 签到与视觉联动流程

1. 学生到达自习室，点击"签到"（宽限期：时段开始前 15 分钟 ~ 开始后 15 分钟）；
2. 后端校验预约状态为"待签到"且在宽限期内；
3. 后端查询视觉检测结果：视觉可用且座位为空 → 提示学生核实（可强制签到）；视觉可用且座位占用 → 签到成功；视觉不可用 → 按时间窗直接签到成功；
4. 签到成功：状态置"已签到"，记录签到时间；视觉定时任务持续关注该座位。

### 6.3 违约与释放流程（定时任务，每分钟）

- **超时未签到**：状态"待签到"且超过时段开始 30 分钟 → 查询视觉结果：座位为空 → 置"违约"（`violation_count+1`，累计 3 次禁约 7 天）；视觉服务不可用 → 释放座位但不计违约；
- **离座释放**：状态"已签到"且视觉连续 30 分钟检测座位为空 → 置"提前结束"，释放座位；
- **疑似占座**：座位无有效预约但视觉连续 10 分钟占用 → 标记并提醒管理员（记录于检测日志）。

### 6.4 定时任务清单

| 任务 | 周期 | 说明 |
|---|---|---|
| 视觉状态同步 | 5s | 轮询视觉服务 /detect，更新 seat.status；状态翻转时写 seat_status_log |
| 超时违约扫描 | 1min | 处理超时未签到预约（区分视觉可用/不可用） |
| 离座释放扫描 | 1min | 结合视觉结果释放已离开用户的座位 |
| 背景重建 | 每日闭馆后 | 调用视觉服务重置背景基准 |
| 日志归档 | 每日 | 清理过期 seat_status_log |

## 七、系统安全设计

### 7.1 认证与授权

- 登录成功后签发 JWT（HS256，密钥置于后端配置，含用户ID、角色、过期时间，有效期 2 小时），前端存储并携带于 `Authorization: Bearer <token>`；
- 后端拦截器统一校验令牌有效性，按角色注解（管理员接口）做权限控制；
- 密码使用 BCrypt 加密存储，禁止明文。

### 7.2 数据安全

- 所有 SQL 通过 MyBatis-Plus 参数化执行，防 SQL 注入；
- 前端 Axios 拦截器统一处理 401（跳转登录）与错误提示；后端统一异常处理返回规范错误结构；
- 输入参数校验（JSR-303 Bean Validation）：学号格式、时段合法性（时段属于该自习室、非过去时段、自习室开放时间内）；
- 关键管理操作（强制取消、座位/时段修改）写入 `admin_audit_log` 审计留痕。

### 7.3 隐私合规

- 摄像头仅用于座位占用判定，**不存储视频流、不采集人脸特征**；
- 检测结果仅保存占用状态、置信度与检测器标识，不保存画面；
- 检测画面预览开关**默认关闭**，开启时对画面进行人脸/区域打码，且仅管理员可见；
- 自习室现场张贴监控告示；`seat_status_log` 按配置期限保留并定期清理。

## 八、测试与部署

### 8.1 测试计划

| 测试类型 | 内容 |
|---|---|
| 单元测试 | 后端 Service 层核心逻辑（预约冲突、状态流转、违约惩戒）、JWT 工具类 |
| 接口测试 | 使用 Postman/Apifox 覆盖全部接口正例、异常例（未登录、越权、参数非法、冲突） |
| 并发测试 | 同一座位同一时段并发预约、同一用户同一时段多座位并发预约（唯一索引兜底）；**必须含"时段重叠/完全相同/跨时段连续"三类用例** |
| 视觉测试 | 不同光照、人数、遮挡、静坐不动场景下的占用判定准确率；背景重置前后对比 |
| 端到端测试 | 完整走通"注册→登录→预约→签到→离座释放→统计"主流程，以及超时违约、取消截止等分支 |

### 8.2 部署步骤

1. **数据库**：执行 `database/init.sql` 初始化库表、时段与测试数据；
2. **视觉服务**：`pip install -r requirements.txt`；配置摄像头地址与座位 ROI；`uvicorn app:app --host 0.0.0.0 --port 8001`；
3. **后端**：修改 `application.yml` 数据库连接与视觉服务地址；`mvn clean package` 后 `java -jar` 运行（或 IDE 直接运行）；
4. **前端**：`npm install` → `npm run dev`（开发）或 `npm run build` 后由 Nginx 托管；
5. **验证**：浏览器访问前端，注册学生账号完成预约签到流程；管理员登录查看统计、审计与视觉监控。
